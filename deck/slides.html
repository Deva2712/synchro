The problem

Why rule-only fraud systems struggle

Fraud changes faster than rules

Fraud patterns change every few weeks. Writing and releasing a new rule takes much longer than that.

False positives cost real customers

If a genuine customer gets blocked, they simply apply somewhere else. This loss never shows up in a fraud report.

There is very little time

The decision has to happen while the customer is waiting on the screen. A few hundred milliseconds is already too slow.

A score alone is not useful

An analyst cannot do much with "risk = 0.87". They need to know why before they can act on it.

So the real requirement is: decide in milliseconds, keep learning without a new release, avoid blocking good customers, and explain every decision.

What I learned while building

Four things that shaped the design

  • Behaviour is harder to fake than documents. A fraudster can buy a stolen PAN, but typing speed, pasting, corrections and how long someone spends on the form are much harder to imitate.
  • Velocity is the strongest signal, and it is cheap. "How many different applicant names used this device today" catches a fraud ring by its 4th application — but only if you count it at the moment of scoring, not in a nightly job.
  • Rules and ML are better together. Rules work on day one and explain themselves. The ML model adapts. An anomaly model catches patterns that nobody has labelled yet.
  • The output should be an explanation, not a number. Evidence, matching fraud type, and what to check next — so the analyst can decide quickly.

What I built

One fast decision with four possible outcomes

✓ ALLOW

Application continues normally. 83% of the demo traffic.

! STEP UP

Ask for OTP or liveness check. Extra friction, not a rejection.

⌕ REVIEW

Held for a fraud analyst, with the case already prepared.

✕ BLOCK

Blocked and raised as a fraud case.

Decision time (p95)22 ms

Only rules and models are in this path. The LLM is called afterwards.

Model accuracy (ROC-AUC)0.939

82% of fraud caught at the review threshold, with a 3.9% false-positive rate.

Learning loopInstant + retrain

An analyst marking fraud blocks that device immediately, and the case is added to the training data.

How the score is calculated

Simple enough to check by hand

risk = 0.55 × ML model probability
     + 0.20 × anomaly score
     + 0.25 × rule score
BLOCKrisk ≥ 0.85, or a hard-block rule fires
REVIEWrisk ≥ 0.60
STEP UPrisk ≥ 0.35
ALLOWbelow that

Weights and thresholds are config, not code

They are read from environment variables, so a risk team can retune them without changing code or redeploying.

Rules combine with noisy-OR

Several weak rules add up to real suspicion, but they can never reach certainty on their own. Only a hard-block rule — for example a device an analyst already confirmed as fraud — forces a BLOCK.

Three models, three jobs

Rules catch what we already know and explain it. The classifier learns from labelled fraud. The isolation forest flags applications that simply do not look like normal traffic.

The 17 signals

What the model actually looks at

Behaviour on the form

Time spent · typing speed · paste events · corrections · tab switches · time of day

A real applicant hesitates and corrects mistakes. A script does not. Someone filling their fifth form of the morning types unusually fast.

Device and network

Emulator / rooted device · VPN or proxy · IP location vs declared address

Weak on their own — plenty of genuine users have a VPN — but useful in combination.

Velocity (counted live)

Applications per device in 24h · per IP in 24h · distinct applicant names per device

These are counted from the database at scoring time, so there is no batch delay.

Credit and identity

Loan-to-income ratio · loan size · account age · email domain age · prior defaults

Left out on purpose

Name, gender, religion, caste, age group, locality. The model looks at behaviour and transaction facts only.

Explainability

Every decision comes with its reasons

RulePlain facts

"Same device used by 5 different applicant names in 24h"
"Form filled by paste/automation (9 pastes at 22 chars/s)"
"Email domain registered 4 days ago"

A rule says what happened, not just a number. This is what an auditor would read.

ModelReal contributions

"Typing speed raises risk (contribution +1.35 log-odds)"

I used logistic regression on purpose. Because it is linear, each feature's contribution is simply coefficient × scaled value — the actual maths of the decision, not an estimate from a separate explainer.

Matching a known fraud type

The case is turned into a vector and matched against a small knowledge base of fraud typologies:

Device farm / application ring similarity 0.81
Suggested control: bind the device fingerprint, block the device across the portfolio, force video KYC for applications sharing it.

So the analyst sees what it looks like and what usually stops it.

One list of evidence

Rule hits and model reasons are merged into a single ranked list, so the API response, the console and the saved record all show the same explanation.

AI layer

The LLM explains the decision, it does not make it

Where it fits

The decision is already made and sent back before Claude is called. It then receives the decision, the rules that fired, the model reasons and the matched typologies, and writes a short summary plus the checks the analyst should do.

Because of this, if the LLM is slow or unavailable, only the wording of the case file changes. The decision itself is never delayed or altered. If there is no API key, a deterministic template is used instead — that fallback is part of the product, not a placeholder.

Guardrails

  • PAN, Aadhaar, mobile, email and card numbers are masked before the prompt is built
  • The system prompt tells it not to invent facts, not to guess masked values, and not to use protected attributes
  • Structured output — it must return fixed fields and one of four allowed actions
  • The output is masked again on the way back
  • 20 second timeout and one retry, then fall back — the call can never crash the decision path

Works on Bedrock too

One environment variable switches between the Anthropic API and the same model on AWS Bedrock. Credentials come from the SDK / IAM role, never from the code.

Source is always shown

The console displays which model wrote the summary (anthropic:claude-opus-5 or rule_based_fallback) and says the decision came from the rules and models.

Vector search

Typology embeddings are stored next to the data (a pgvector column in production). Switching to Bedrock Titan embeddings only changes one function.

Learning from analysts

How the system improves over time

Step 1 — immediate

Analyst confirms fraud

The device and IP are denylisted for the whole portfolio starting from the very next application, using a hard-block rule. No retraining or deployment needed.

Step 2 — on demand

Retrain

Every labelled case is added to the training data with 12× the weight of a synthetic sample. Only an admin can trigger it, it is logged, and the response shows the old and new metrics side by side.

Step 3 — safety check

Promote only if it is not worse

If the new model loses more than 0.01 ROC-AUC compared to the current one, it is not promoted. The API reports this and the old model keeps running.

In testing with a single labelled case, ROC-AUC moved from 0.9386 to 0.9339. That is within the noise you would expect from one sample, and below the promotion bar, so the model was not swapped. I added this check after seeing that a few bad labels could otherwise quietly make the system worse.

Security and responsible AI

Handled in the code, not just mentioned

Security

  • Login JWT tokens (HS256, 60 min), passwords hashed with scrypt and a per-user salt, compared in constant time
  • Roles analyst vs admin; only an admin can retrain the model, and it is logged
  • Input validation strict schemas — number ranges, IPv4 check, fixed options, and unknown fields are rejected
  • Rate limiting per client on login and scoring
  • No hardcoded secrets everything comes from environment variables; .env is git-ignored and .env.example is blank. With no JWT secret set, a random one is generated instead of using a default
  • CORS a fixed list of allowed origins, never *

Responsible AI

  • The LLM never decides — rules and models decide, it only explains
  • PII is masked before anything is saved or sent to a model
  • No protected attributes in the features, and the prompt forbids using them
  • Human in the loop — suspicion leads to extra verification; only an analyst can confirm fraud
  • Auditable — features, scores, rules, evidence and the summary are saved per application, so a decision can be explained later
  • Source shown — the console names the model that wrote each summary

How the code is organised

Engineering practices I followed

API first

Every feature is an API endpoint with auto-generated OpenAPI docs at /docs. The React console is just one client; a loan origination system could be another. Nothing is only reachable through the UI.

One file, one job

features · rules · model · knowledge · llm · decision · security · schemas · db · config. The decision is assembled in one place, and the feature order is defined in one place because the model depends on it.

Configuration, not constants

Weights, thresholds, model name, rate limits, database URL and LLM backend all come from the environment. The same code runs on SQLite locally and PostgreSQL + pgvector in the cloud.

20 tests

Decision thresholds, rules and their wording, PII masking, login and roles, and input validation (bad IP, negative amount, unknown field). Two of them test the behaviour that matters most:

▸ six applications from one device must escalate by the last one
▸ after fraud is confirmed, the next clean-looking application from that device must be blocked

Easy to run

make setup · make api · make web · make demo · make test

The first start trains the model and loads the knowledge base automatically. No cloud account or API key is needed to try it — the AI layer falls back to its offline path.

Summary

What this prototype shows

Against the problem statement

  • Real time — 22 ms p95, fast enough to run inside the application flow
  • Self-learning — analyst verdicts block devices instantly and retrain the model, with a safety check before promotion
  • Fewer false positives — four outcomes, so suspicion costs an OTP instead of a customer
  • New fraud patterns — an anomaly model that does not need labels
  • Customer trust — PII masked, no protected attributes, every decision explainable
